# Design: Glass Box — see the investigation, verify it yourself, share the replay

Generated by /office-hours on 2026-09-10 (revision 3: built, QA'd; two adversarial review rounds)
Branch: feat/glass-box
Repo: advait27/EADIP
Status: IMPLEMENTED on feat/glass-box (see ADR-0014; QA report .gstack/qa-reports/)
Mode: Builder

## Problem Statement

EADIP is a finished, well-tested governed-AI investigation engine that nobody can
see working. It only speaks curl and SSE, every AI seam defaults to keyword
heuristics, and a run only makes progress while a client holds the SSE stream open.
The platform's thesis is "never take the AI's word for it", but a reader today has
to take the server's word that verification happened.

The upgrade makes the engine visible, makes verification something the READER does
in their own browser, and makes any run shareable as a one-link replay.

## What Makes This Cool

- **Live evidence graph.** A run renders as an animated graph while it happens:
  goal, plan steps, findings, claims, sources, recommendations, with provenance
  edges. You watch the analyst think.
- **Verify in your browser.** Click any number. The exact SQL behind it re-runs
  inside the page via DuckDB-WASM against the tenant-scoped rows the server hands
  over, and the page shows "matches" or "conflicts". Trust moves from the server to
  the reader.
- **One-link replay.** Every run gets a share token. Opening it replays the
  investigation from the persisted event log, with timing, no login needed.
- **Bring your own CSV.** Drop a file, ask a question about it, watch the same
  pipeline investigate your data.
- **The AI path is tested.** The LLM planner, interpreter, reflection, SQL
  generator, query expander and recommender are unit-tested behind a fake model
  client, and the two factories that ignored tier routing now honour it.

## Constraints

- Keep every existing gate green: ruff, mypy, the 289 collected tests (274 pass, 15
  skip without external services), eval, safety, reliability, load, bandit. No
  engine rewrite.
- Ports-and-adapters stays: new persistence (event log, dataset registry) gets a
  port and an in-memory adapter now; the Postgres adapters are a documented
  follow-up (ADR records it).
- Offline by default: the UI and all new tests run with no external services and no
  model key. DuckDB-WASM assets are copied from `node_modules` into the Vite build
  and served locally, never from a CDN.
- Tenant isolation, residency and RBAC apply to every authenticated new route. The
  share route replaces RBAC with a signed, scoped, expiring token and still applies
  the residency check for the tenant named in the token.
- Python 3.13, FastAPI, Pydantic v2 on the backend. Vite + React + TypeScript on the
  frontend, built into the Python package so one image ships both.

## Premises

1. A UI over the existing SSE event contract is enough to show the engine; no new
   orchestration semantics are needed for the visible part.
2. Decoupling run execution from the SSE request is a prerequisite for any UI
   (reconnects, refresh, share) and for multi-replica deployment.
3. Client-side re-execution of provenance SQL over a tenant-scoped row bundle is an
   independent re-check of the *arithmetic* over rows the server supplied, not an
   independent verification of the data. The bundle rows are fetched with SQL
   rendered by `TemplateSqlGenerator.render` and passed through `SqlSafetyValidator`
   before `warehouse.execute` (the same governed read path the server's own
   recompute uses), so they are the rows the server would verify against, but a
   reader still has to trust the server for them. (Corrected 2026-09-27; the
   original wording called this "a legitimate independent verification".)
   Snapshot commitment: at verification time the verifier hashes each touched
   table's rows in a canonical form (`verification/commitment.py`, mirrored in
   `web/src/lib/commitment.ts`) and records the hashes on the run
   (`RunState.snapshot_commitments`, also in the `verification.summary` event). The
   bundle states each table's `sha256` and the recorded commitments; the browser
   re-hashes the rows and marks claims on a mismatching table `tampered`. Limit:
   this detects rows that changed between verification and sharing, and lets a
   reader compare against a commitment obtained through another channel. It does
   not protect against a server that lies consistently at verification time,
   because the commitment comes from the same server as the rows.
4. The demo dataset is fine for the first cut; CSV upload is the last item because it
   touches analytics interpretation the most, and it is DuckDB-only in this cut.

## Approaches Considered

### Approach A: Glass Box (chosen)
Live evidence graph UI + verify-in-browser + share replay + CSV upload + tested LLM
path. Reuses SSE events, RunState, VerifiedClaim provenance, DuckDB, service-JWT
signing, audit log. Effort L. Risk Med (frontend surface, WASM size).

### Approach B: Adversarial Court (not chosen)
Prosecutor/defender/judge multi-agent verification with a caught-error metric.
Rejected for this round: deepest novelty but invisible without a UI, and 3 to 5x
model calls per claim. Natural follow-up once Glass Box exists to show it.

### Approach C: Ambient Analyst (not chosen)
What-if simulation over the lineage graph plus scheduled anomaly watchers pushing
briefs to Slack. Rejected for this round: needs the background worker this design
introduces anyway; revisit after.

## Recommended Approach: architecture

### Backend (Python, `src/eadip`)

1. **Run executor + event log** (`orchestrator/executor.py`, `ports/events.py`,
   `adapters/memory_event_log.py`).
   - `EventLog` port: `append(run_id, event) -> LoggedEvent`, `read(run_id, after_seq)`,
     `last_seq(run_id)`, `stream(run_id, after_seq)` (replay then live tail).
     `seq` is per-run, 1-based, monotonic. SSE messages carry `id: <seq>`;
     `Last-Event-ID: N` replays from `seq > N`. A cursor ahead of the log is clamped
     to the head (replay nothing, tail everything new). Subscribe happens before the
     replay snapshot, with no await in between, so no event is lost or duplicated.
   - The in-memory log keeps at most `event_log_max_runs` (default 500) runs; when
     exceeded, the oldest terminal run's events are evicted. The retention sweep
     (`platform/retention.py`) is the production path for the Postgres adapter.
   - `RunExecutor` starts `orchestrator.stream(state)` as an `asyncio.Task` on
     `POST /v1/runs`; every yielded `Event` is appended to the log, then each
     `on_event` hook runs. The two hooks that live in the SSE route today move here:
     notification fan-out and budget charging (the executor charges
     `state.tenant_id`; memory consolidation already lives inside the orchestrator).
     On an unhandled exception the executor appends a synthetic `run.failed`
     `{error}` event and saves the checkpoint as FAILED. The concurrency gate is
     acquired at start and released in the task's `finally`.
   - Terminal events, by event type not by polling state: `run.done`, `run.failed`,
     `approval.required`.
   - `GET /v1/runs/{id}/events` becomes a subscriber: replays from `Last-Event-ID`
     (or 0), then tails while the executor is running the run, ending after a
     terminal event. **Invariant:** a GET on a finished or paused run replays
     everything and closes; a GET on a live run tails to the next terminal event.
     The route still records the `run.stream` audit action. Same event names and
     payloads as today, plus `id:`.
   - The 429 from the concurrency gate moves from `GET /events` to `POST /v1/runs`
     (the setting keeps its name, `max_concurrent_streams_per_tenant`, and now
     bounds in-flight runs per tenant; the load harness expects 202 from POST and
     only ever runs 100 tenants with one run each, so it is unaffected).
   - `POST .../approvals/{id}` applies the decision, then calls `executor.resume`
     for an approval; `resume_url` stays in `DecisionResponse` for compatibility and
     points at the tailing subscriber.
   - Run status is read from the checkpoint (`RunState.status`), as `/report` does
     today. The `Run` repository row is not updated in this cut.
   - Startup: the executor resumes any non-terminal checkpoint the store can list
     (in-memory: none; Postgres path documented in the ADR).
   - **Compatibility with stream-driven tests.** `tests/unit/test_gateway.py`,
     `test_runs_orchestration.py`, `test_approval_route.py`, `test_run_report_route.py`
     and `src/eadip/eval/load.py` all open one stream and expect `run.done` in it,
     then assert side effects. Under the executor, POST starts the run and the
     stream replays from 0 and tails to `run.done`, so the bodies are identical.
     `_drive` after an approval works because the decision route resumes and the
     second GET tails to `run.done`. `tests/conftest.py` switches to
     `with TestClient(app) as client` so one event loop spans all requests in a
     test. `src/eadip/eval/safety.py` calls the orchestrator directly; unaffected.
2. **Timeline + evidence graph** (`orchestrator/graph.py`, routes in
   `gateway/routes/runs.py`).
   - `GET /v1/runs/{id}/timeline` returns the ordered event log.
   - `GET /v1/runs/{id}/graph` returns `{nodes, edges}` derived by a pure function
     `build_evidence_graph(state: RunState)`: question, goal, steps, findings,
     claims (verification status + confidence), evidence (sql | passage | tool),
     recommendations. Node ids are stable strings (`goal`, `step:<id>`,
     `finding:<n>`, `claim:<n>`, `evidence:<sha1[:12]>`, `rec:<n>`). Edges carry a
     `relation`: `plans` (goal→step), `produces` (step→finding, via
     `Finding.step_id`), `cites` (finding→evidence), `verifies` (claim→finding,
     joined on `(claim text, first provenance ref)`), `supports` (rec→claim, via
     `Recommendation.based_on` claim text).
3. **Evidence bundle** (`verification/bundle.py`, route
   `GET /v1/runs/{id}/evidence-bundle`).
   - `VerifiedClaim` gains `detail: dict` (copied from the finding by the verifier)
     so the bundle carries each claim's re-derivation recipe without a join.
   - For every analytics claim with SQL provenance: `{claim_index, sql, tables,
     claimed_magnitude, recomputed_magnitude, kind, detail}`. Tables are parsed
     from the SQL with sqlglot.
   - Per referenced table, a tenant-scoped row bundle rendered as
     `TemplateSqlGenerator.render(QueryPlan(table, dimensions=<all columns>))`
     (explicit columns, tenant literal), passed through `SqlSafetyValidator`, then
     executed through the warehouse with `row_cap = analytics_row_cap` (10000, the
     same cap the server's verifier uses). `truncated` is reported; the UI then
     shows "cannot verify in browser (sampled)" rather than "conflict".
4. **Share links** (`gateway/routes/share.py`).
   - `ServiceTokenIssuer` grows `mint_claims(claims, ttl_s)` and `verify` stays.
   - `POST /v1/runs/{id}/share` (analyst, audited `run.share.create`) mints an HS256
     token `{run, tenant, scope: "replay", jti, exp}` with `share_link_ttl_s`
     (default 7 days) and returns `{token, url, expires_at}`.
   - `GET /v1/share/{token}` takes no identity header. It verifies the token, applies
     the residency check for the token's tenant (451 elsewhere), loads the
     checkpoint, and returns `{run_id, question, status, timeline, graph, brief,
     bundle}` read-only, audited as `run.share.view` with `actor="share:<jti>"`.
     Bad or expired tokens are 404. Revocation before expiry is deferred.
5. **LLM path, trimmed to what Glass Box needs to be honest about "the AI is real".**
   - `tests/fakes.py`: `FakeModelClient` with scripted responses and recorded prompts.
   - `agents/llm.complete_json(client, prompt, *, model, validate: Callable[[dict], T]
     | None)`: when `validate` raises, retry once with the error appended to the
     prompt; return `None` after that. Planner, interpreter and reflection adopt it.
   - Unit tests for `complete_json`, `LLMPlanner`, `LLMGoalInterpreter`,
     `LLMReflection`, `LLMSqlGenerator` (strip + repair feedback), `LLMQueryExpander`,
     `LLMRecommender`, and `LiteLLMClient.complete` with `litellm.acompletion`
     monkeypatched.
   - `analytics/factory.py` and `retrieval/factory.py` route their model through
     `ModelRoutingPolicy` (`SQL_GENERATE`, `QUERY_EXPAND`); the orchestrator factory
     already does.
6. **Datasets (CSV bring-your-own)** (`ingestion/datasets.py`, route
   `POST /v1/datasets`, `GET /v1/datasets`). DuckDB-only in this cut: on the
   Postgres warehouse backend the route returns 501.
   - Parse with stdlib `csv`. Reject files over `dataset_max_bytes` (5 MB) or with
     more than `dataset_max_columns` (32). Header normalisation: lowercase,
     `[^a-z0-9]+ -> _`, strip leading digits/underscores, must match
     `[a-z][a-z0-9_]*`; reserved SQL words and allow-listed function names get a
     `_col` suffix; a source column named `tenant_id` is rejected; duplicate names
     after normalisation get `_2`, `_3`. Types: `number` when every non-empty value
     parses as float, else `text`. The period column (first column whose name
     contains `period|quarter|month|date|year`, else the first text column) is
     forced to `text` so recompute's "one numeric column" inference holds.
   - Logical table name = slug of the filename (same normalisation, without the
     reserved-word suffix); physical DuckDB table = `ds_<tenant_hex8>_<slug>`, with a
     `tenant_id VARCHAR` column injected, created under the seed lock. Uploading the
     same logical name replaces the table.
   - `DatasetRegistry` port (in-memory adapter) maps `(tenant_id, logical name) ->
     (physical name, TableSchema, period_column, row_count)`. The registry is
     process memory: after a restart the `.duckdb` file may hold orphan `ds_*`
     tables; they are unreachable because the validator allowlist comes from the
     registry, and the startup path drops any `ds_*` table not in the registry.
   - `DuckDBWarehouse.schema(tenant_id)` returns the demo table plus that tenant's
     registered tables, so the validator allowlist includes them. Logical→physical
     mapping is applied after validation by a sqlglot table rename.
   - `SqlSafetyValidator._check_columns` becomes per-table when exactly one base
     table is referenced (the union check stays for joins).
   - `AnalyticsService._interpret` picks the table whose logical name or slug is
     mentioned in the question (longest match wins), else the default. For a
     registered table: the metric map is built from its numeric columns
     (`{col: (col, col)}`), `_METRICS` applies only to `finance_metrics`; the metric
     is the numeric column named in the question, else the first numeric column;
     the dimension is the text column (not the period column) with the lowest
     cardinality among the sampled rows; `period_column` and `filter_column` come
     from the chosen `TableSchema`, and a filter value is lifted from the question
     only when that table has the filter column and the value occurs in it.
   - A `TableSchema` gains an optional `period_column` hint so the executor does not
     have to pass request defaults.

### Frontend (`web/`, Vite + React 19 + TypeScript)

- Routes: `/app` (ask), `/app/runs/:id` (live graph + brief + verify panel +
  approvals), `/app/share/:token` (replay, no auth), `/app/datasets` (upload).
- Graph: `d3-force` layout rendered in SVG; nodes fade in with CSS transitions as
  events arrive. Colors by node kind; claim nodes tinted by verification status.
- Verify panel: lazy-loads `@duckdb/duckdb-wasm` (wasm + worker copied from
  `node_modules` at build time and referenced by local URL), creates the bundle
  tables with the server's column names and DOUBLE/VARCHAR types, runs each claim's
  SQL, compares to the claimed magnitude with the server's relative tolerance, and
  shows "verified in your browser", "conflict", "cannot run" or "sampled".
- Replay (MVP): fetches the share payload and plays events with their original
  relative timing at 1x, plus an "instant" button. Scrubber and speeds are a
  follow-up.
- Dev identity (P2, small): the UI sends `X-Roles: analyst approver` in dev mode with
  a header switch, so the approval flow can be demoed.
- Build output goes to `src/eadip/gateway/static/app`, git-ignored; FastAPI mounts
  `/app` with SPA fallback when the directory exists, and `/` redirects to `/app`
  when built, else `/docs`. The wheel includes `static/app/**` when present.
- Dockerfile: a node stage builds `web/` first and its output is copied into
  `src/eadip/gateway/static/app` before the Python build stage runs `uv sync`.
- Tooling: `make web` (npm ci + build), `make web-dev` (vite with proxy to :8000),
  `make web-test` (tsc + vitest); CI job `web`.

## Built vs. designed (decision record)

- Round-2 review items landed in code: replayed terminal events no longer end a
  tail (only a NEW terminal event does); the bundle row fetch renders with
  `group_by=False`; `TableSchema` carries `period_column`/`dimensions`/
  `sample_values` profiled at upload; the logical→physical rename happens in
  `DuckDBWarehouse.execute`; the wheel lists the UI as a hatch artifact; share
  tokens are refused unless `scope == "replay"` with `run`+`tenant`; the demo
  table name is a 409; empty headers become `col_<n>`; every approval decision
  resumes; `GET /v1/runs/{id}` gives status + log head; the bundle is a lazy
  sibling route on share; `LLMRecommender` really calls the model and grounds
  every action; only the `eh` wasm ships (36 MB → 6.4 MB brotli).
- Found while building: findings now carry `period_column`/`dimension`, and
  both recomputes prefer the declared period column (dimension/period ties
  mis-verified an uploaded table). The registry doubles as a tenant-scoped
  vocabulary so a question naming a dataset plans an analytics step.
- Deferred (unchanged): Postgres event log + dataset registry, share-link
  revocation list, replay scrubber/speeds, `resume` refusal on capacity returns
  the decision and the next stream open resumes lazily (not implemented; the
  gate is per tenant and the paused run already holds no slot).

## Open Questions

- Postgres `EventLog` and `DatasetRegistry` adapters: documented follow-up in the ADR.
- Share-link revocation beyond expiry (a revocation list) is deferred.
- DuckDB-WASM bundle choice: `eh` when supported, `mvp` fallback; verify total asset
  size stays under about 12 MB.

## Success Criteria

- Open `/app`, ask "Why did EMEA gross margin fall last quarter?", watch the graph
  build live, see the brief render, click a claim, see "verified in your browser".
- Copy the share link, open it in a private window with no headers: the replay plays.
- Upload a CSV with a numeric and a period-like column, ask about the numeric
  column, get a driver breakdown with SQL provenance.
- Refreshing the run page mid-run reconnects and catches up from `Last-Event-ID`.
- `make lint type test eval safety reliability` all green; new unit tests cover
  event log, executor, graph builder, evidence bundle, share tokens, LLM path,
  dataset inference; `tsc` and vitest green.
